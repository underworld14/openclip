## Current behavior

ImportPanel.tsx:99 renders `{ctl.stage} · {ctl.pct}%` where stage is a lowercase internal token from import-pipeline.ts:54,59,72 ('probing' / 'extracting' / 'transcribing'). No elapsed time, no ETA, no file size. import-pipeline.ts:109 discards the byte counts the download runner computes: `onPartial: (data) => opts.onProgress?.(data.pct, 'downloading')`. On the export side, export-runner.ts:151 emits `progress(0, 'analyzing')` once and nothing further until encoding starts — for a reframe+silence clip that is an unbounded frozen 0% bar, and it is the slowest phase (up to four separate decodes of the span with no plan cache).

## Desired behavior

A named stage checklist rather than one bar: Import ✓ → Extract audio ✓ → Transcribe (live, 62%) → Find clips. Human labels, elapsed time per stage, byte counts and MB/s during downloads, and a realistic up-front estimate. Sub-progress during 'analyzing' (frames sampled / total) so it never sits at zero.

## Competitor precedent

OpusClip surfaces a named stage machine (IMPORT/CURATE/REFINE/RENDER/UPLOAD) plus an estimated wait. LokaClip shows a 6-stage strip (Unduh → Potong → Framing → Subtitle → Watermark → Finalisasi). YT-Short-Clipper uses horizontal numbered step cards with per-step bars and a green check on completion.

## Implementation sketch

New `components/StageProgress.tsx` fed by a `STAGE_LABELS` map ('probing'→'Reading video', 'extracting'→'Extracting audio', 'transcribing'→'Transcribing', 'analyzing'→'Analyzing faces & silence', 'encoding'→'Rendering'). Stop discarding bytes at import-pipeline.ts:109 — widen `onProgress` to `(pct, stage, detail?)`. In export-runner.ts, emit incremental progress from inside the reframe frame-sampler loop (reframe-detect.ts already streams rawvideo frames — count them against the known frame budget) so 'analyzing' moves. Track a `startedAt` per stage in the controller for elapsed display.

## Done

**Human stage names.** `STAGE_LABELS` + `stageLabel()` in `components/jobStatus.ts`
map every token any runner emits ('probing' → "Reading video", 'analyzing' →
"Analyzing", …). Both the status bar AND `ImportPanel` render through it, so the
two surfaces cannot describe the same stage differently. An UNKNOWN token is
title-cased rather than dropped — a future runner stage should read slightly
awkwardly, never as a lowercase identifier. `job-status.spec.ts` asserts the map
covers every token grepped out of `src/main`.

**A checklist, not one bar.** `stageChecklist()` walks the stage sequence the
caller declared at begin time (a URL import prepends 'downloading'; an export
only includes 'analyzing' when reframe or silence-removal is on, mirroring the
runner's own `willAnalyze` branch). A stage passed without ever being observed
still counts as done — position in the sequence is the authority, not whether the
UI happened to catch the event.

**Bytes.** `runUrlDownload` was collapsing `{downloadedBytes,totalBytes,pct}` to
just the percent. `onProgress` is now `(pct, stage, detail?)` all the way through
`runImportPipeline` → the controller → the task, so the bar shows
"12 MB of 140 MB · 2.1 MB/s" from numbers the app already had.

**'analyzing' moves.** `detectFromFrameChunks` already walked frames one at a
time and the budget is knowable (`ceil(duration * sampleFps)`), so an `onFrame`
hook threads out through `detectReframe` → `planReframe` → the export runner,
which maps it into a 0..`ANALYZE_PROGRESS_CEILING` (15%) band. The ceiling is
deliberately small: face sampling is slow but it is not most of the work, and a
bar that reaches 60% before encoding even starts is a worse lie than one that
moves a little.

**ETA.** `estimateEta()` extrapolates from elapsed vs percent and returns null
outside a 5–97% band or in the first three seconds. A missing ETA reads as
honest; a wildly wrong one reads as broken.
